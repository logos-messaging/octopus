Logos Delivery

The problem

CI minutes cost money, and our own machines sit idle

  • GitHub-hosted runners bill by the minute. macOS minutes cost the most.
  • Every developer has a fast machine that is idle most of the day
  • Self-hosted runners exist, but:
    • registering one needs repo admin rights
    • to add them for each job, a server must hold a GitHub admin token
  • We want team machines to run the CI, with no server and no stored admin token

Where can CI run?

✗ GitHub-hosted runner

paid per minute, so we keep it only as the fallback

✗ Self-hosted runner

needs repo admin rights, or a server that holds an admin token

✓ Team machine with Octopus

idle, owned by a team member, no admin token

The idea

Logos Delivery is the control plane

  • There is no server in the middle. The team machines and the submit job meet on a Logos Delivery topic.
  • Discovery, test job assignment, results and live logs all go over Logos Delivery
  • GitHub only proves who asks, with an OIDC token. No runner registers with GitHub.
  • Each test job that no team machine takes, and Windows, goes to a GitHub-hosted runner

Discovery

who is online, which OS

Assignment

claim · lease · takeover

Results & logs

encrypted reply channel

Octopus is written in Python. It calls liblogosdelivery through logos-delivery-python-bindings (cffi, NodeWrapper).

The submit job runs Octopus on a GitHub-hosted runner. Team machines verify the token against GitHub's public keys and rank themselves (rendezvous hash). One claims the test job, runs .octopus/ci.sh, and streams the log back. The submit job prints the log and passes or fails the PR check.

How it works

A CI run over time

If a team machine stops during a run, its lease expires and another team machine takes over with a higher epoch. The epoch stops the old owner from reporting a result. A network partition can still make a test job run twice.

Logos Delivery API

All of the Logos Delivery API that we needed

node = NodeWrapper.create_and_start(
    {"mode": "Core", "preset": "logos.test"},
    event_cb=on_event)        # one callback, all events

# messaging
node.subscribe_content_topic(topic)
node.send_message({"contentTopic": topic,
                   "payload": b64(data), "ephemeral": False})
# on_event: message_received

# reliable channels
node.channel_create(chan, topic, sender,
                    encrypt_fn=enc, decrypt_fn=dec)
node.channel_send(chan, {"payload": b64(data)})
# on_event: channel_message_received | _sent | _lost
node.channel_close(chan)

node.stop_and_destroy()
  • Seven calls and one event callback
  • The logos.test preset gives the cluster, the shards and the entry nodes
  • All of the Logos Delivery code in Octopus is one file of 511 lines, with threads and restarts
  • A new node joins and sends messages in about 4 s
  • No open ports. Team machines behind home NAT work.

Reliable-channel API

Reliable channels: private logs and results

Where

  • Log lines from the team machine back to the submit job, live
  • The result of the test job: pass, fail, exit code

Why

  • The result decides whether the PR passes, so it must not be lost
  • Only the submit job can read the log, because it can contain secrets
  • A submit job that connects late or reconnects must catch up

How

  • channel_create / channel_send / channel_close, one channel between a team machine and the submit job
  • Octopus plugs in its own cipher, keyed from the reply key and the machine key
  • The library acks and retries. The team machine replays its buffer on hello.

We learned that the “sent” event of a channel needs a Store node. So our tests check delivery only.

Reliable channels · how 2 of 3

Our cipher, the library’s transport

Both sides derive the same channel key from the two public keys (X25519). This needs no extra round trip. The library decrypts each segment on its own, so every segment carries its own nonce. Only the two key holders can encrypt or decrypt, and a segment that fails to decrypt is dropped.

Reliable channels · how 3 of 3

Logs: buffered, then replayed on hello

The team machine keeps its log buffer, so a submit job that connects late, or reconnects, gets the whole log in order. The reliable channel acks and retries what is lost.

Messaging API

Messaging: announce, ask, and be heard

Where

  • Announces: which team machines are online, idle or busy, every 10 s
  • The signed team member list, so team machines know who belongs
  • Requests from the submit job, then claims and leases between team machines
  • Done messages when a test job ends

Why

  • One topic reaches each team machine online. There are no addresses and no registry server.
  • These messages repeat or are idempotent, so best-effort delivery is enough
  • Authenticity comes from signatures in Octopus, not from the network

How

  • subscribe and send_message on content topics under /octopus/1/
  • Library events are handed to a worker thread and de-duplicated
  • A restart of the Logos Delivery node replays every subscription
  • All on one topic of the public logos.test network

Messaging · flow 1 of 2

Announces: who is online, and how busy

The submit job runs on a GitHub-hosted Linux runner. It joins the Logos Delivery network, listens to the announces, and decides. Team machines announce every 10 s if they are busy. With no team machine of the OS online, the submit job gives up after about 25 s. With an idle one, it waits up to 45 s for a lease. With all busy, it waits up to 240 s. Then it falls back to a GitHub-hosted runner.

Messaging · flow 2 of 2

Events and restarts

Events: handed to a worker thread, de-duplicated

Restart: the node is recreated and every subscription is replayed

The library thread never waits for a handler, and a restart loses no subscription.

What we learned

What went well, what can be better

Went well

  • A fresh node joins the public network and exchanges messages in about 4 s
  • Team machines behind home NATs reach each other through the network, with no ports to open and no server
  • The library does the acks and retries for our reliable channels, with our own cipher
  • Running the real library in CI found crashes at exit and shared state early

Can be better

  • A runtime log level that works, and a quiet default
  • A fast, clean stop: no 24 s wait, no leaked context
  • State in a per-node path by default, not ./data of the working dir
  • Library limits that are visible and settable (peers per IP)
  • Prebuilt libraries for Windows, and bindings that need no repo checkout

What we learned

We used it on itself

  • Octopus runs its own CI through Octopus
  • We installed it as new users and filed what hurt
  • Fixed during the hackathon:
    • library 279 MB → 68 MB (stripped)
    • TRACE logs, about 360 lines a second → INFO by default
    • stop took 24 s → immediate
    • clear errors for missing gh login and tokens
  • Still open:
    • a node keeps ≤ 5 peers per IP (library limit)
    • nightly end-to-end test needs its repo set up
  • Two ways to use it, one CLI:
    • octopus ci init: join the team CI
    • octopus init: a plain runner for a repo

Where it stands

Status and next

  • v0.4.0 released: pip wheel, prebuilt libraries for Linux x86_64 and macOS arm64
  • octopus update upgrades a machine and restarts its service
  • Next:
